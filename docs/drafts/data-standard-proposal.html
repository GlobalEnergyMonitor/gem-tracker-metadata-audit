A canonical data format for GEM projects

Discussion draft for the data team, September 2026. Nothing here is built; this is a possible route forward.

1. The problem

GEM's project data lives in the research database as one nested record per project: the project, its units, their owners and the owners' parents, status timelines, locations, sources. Everything anyone sees is a different flattening of that record: the tracker download sheets, the datahub releases, the wiki, internal grids, analysis snapshots. Each flattening is maintained by hand, with its own column names and its own rules for what a value means.

The tracker metadata audit measured the result across 30 trackers: 741 distinct field names, of which only 51 are shared by five or more trackers, and status alone appears under eight different names. Three header conventions coexist. The parenthetical in a column header carries five unrelated meanings.

2. The proposal

Define one canonical document format for a GEM project and build every other artefact from it.

  • One document per project, nested the way the data actually is: project, units, owners with their parent tree, timelines, sources, location. Entities (companies, governments) are documents in their own right as well.
  • A core shape shared by all project types, plus an extension per type (combustion, solar, wind, nuclear, geothermal, hydro, steel, LNG, oil and gas extraction) adding that type's fields. This mirrors how the database is built.
  • Codelists published alongside: every vocabulary (status, fuel, technology, country, entity type, and so on) as a CSV of code, title and description. Each list is either closed, where an unknown code is an error, or open, where it is a warning.
  • Readable codes, not database ids. A status is retired, a country is GBR, a fuel is bituminous.
  • Stable identifiers. GEM's existing ids (L… projects, G… units, E… entities) become the standard's ids, with an identifiers list carrying every other scheme such as WEPP, LEI and PermID.
  • Snapshots are collections of documents, not database dumps: a manifest, one file per document type, and the codelists as they stood on that date.
  • Documentation generated from the schema, so reference tables and codelist pages cannot drift from the definitions.
  • Import as well as export. A document can be loaded back into the database without loss, because every field in the schema has a known home in the data-entry form.

The format would be defined as a JSON Schema: a machine-readable description of which fields exist, their types, and which codelist each coded field draws from. A validator checks documents against it and applies the extra rules a schema cannot express, such as dates in the future or shares that do not add up. Because GEM is the only publisher, there is no need for committees or registries; the format can change quickly as long as every change is logged.

3. What it would give us

  1. A single contract between the database and everything downstream. Downloads, datahub, wiki and analysis read one documented shape.
  2. Lossless round trips. Bulk edits, migrations and research-team corrections stop being per-column spreadsheet mappings.
  3. Point-in-time comparison across snapshots, because every snapshot is the same shape.
  4. Field standardisation with teeth. A name exists once, in the schema, with its definition; a sheet column is a projection of it.
  5. A way in for trackers not in the database yet. Coal mines, terminals, cement and others would each be an extension when they join.

4. How it fits with the metadata audit

The audit chose two existing conventions: Table Schema, a way of describing the columns of a table (name, type, definition, allowed values, unit), and DCAT, a way of describing a dataset as a whole (title, publisher, licence, dates covered, files). Both are the right tools for tables, and the tracker spreadsheets are tables. The research database is nested, and JSON Schema is the right tool for a nested document. The two compose:

  • The audit's field properties (definition, code-friendly name, type, unit, allowed values with definitions, accuracy companion, category, taxonomy tag) become annotations on each field of the JSON Schema. The coal plant and coal mine trackers already have complete field metadata of this kind, which the audit uses as its reference for the others. That coal plant metadata is, in effect, the field dictionary for the combustion extension, already written.
  • A flattened spreadsheet projection of the document is a table again, and its Table Schema is generated from the JSON Schema. Same names, same definitions, one source.
  • The audit's extracted reference sets (country, status, fuel category) become the published codelists, and its out-of-set checks read the same files.
  • The snapshot manifest is a DCAT dataset description.

Three coal plant fields, as the audit defines them and as they would appear in a document:

Document field Audit field and definition What changes
capacity: {value: 543, unit: MW} capacity_mw, "Nameplate/gross/installed capacity, in megawatts" The unit moves from the name into the value, so LNG and steel can use the same shape with different units.
status: retired status, allowed values operating, retired, cancelled, construction, announced, shelved, permitted, pre-permit, mothballed The allowed values become the closed status codelist. The audit's list and the database's list differ today; the published codelist makes that visible.
retiredYear: {year: 2024, period: H2} retired_year, "Year the unit was decommissioned" The document keeps the half-year the database knows; the spreadsheet projection keeps only the year.

Things to notice, compared with how the database stores this today:

  • Location, owners and operators sit on every unit, never on the project. Entering them once at plant level is a data-entry convenience, and the exporter expands it.
  • Every code is a readable word where the database stores a number.
  • Owners carry the whole company, its identifiers and its parent tree, where the database stores a company id.
  • A date known only to a half-year is a {year, period} pair, where the database has separate year and month columns.
  • Sources are objects with a short name and URL, where the database has an id list.
  • Search columns, compressed copies and empty template rows are absent.

6. Decisions taken so far in discussion

Topic Decision
Audience Internal canonical format; every external artefact built from it. No other publishers expected.
Structure Core plus per-type extensions, generated from the models where possible, hand-named where not, with a drift test.
Scope The nine types in the database for v1; extension mechanism admits new types.
Identifiers GEM L/G/E ids with a scheme prefix, plus an identifiers list for external schemes.
Coded values Code only, as stable readable strings. Codelist tables gain an immutable code column.
Reference data Turbine manufacturers and nuclear models become reference-data documents, not codelists.
Ownership Owners embedded in full with the whole parent tree; separate GEM-parent and ultimate-parent fields.
Entities Also exported as their own documents, alongside projects.
Location, owners, operators Unit level only.
Sources Inline objects at every citation; a lighter projection without them.
Time Current state only per document; history by comparing snapshots.
Snapshot layout One directory per snapshot: manifest, one JSON Lines file per document type, codelists folder.
Naming camelCase everywhere, including spreadsheet headers.
Change policy Breaking changes allowed, every change logged.
